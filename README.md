# 한국농산 캡스톤 디자인 기획 자료

한국농산 캡스톤 디자인 프로젝트의 팀원별 초기 기획 자료를 모으는 저장소입니다.

이 저장소는 팀 기획안을 통합하기 전에 세 명의 팀원이 각자 조사한 내용, 아이디어, 미팅 질문과 개발 계획을 공유하는 공간입니다. 개인 문서는 원본 그대로 관리하고, 통합 기획서는 팀 논의 후 별도로 작성합니다.

## 1. 저장소 운영 원칙

이 저장소는 프로젝트의 공식 문서 기준점으로 사용합니다. 기획, 일정, 회의 결과, 협업 규칙과 주요 결정은 구두로만 남기지 않고 이 저장소에 기록합니다.

- README는 저장소 구조와 협업 규칙의 기준 문서입니다.
- 개인 기획은 `docs/<이름>/`에서 작성자별로 관리합니다.
- 팀 합의 전에는 개인 의견을 확정된 요구사항처럼 표현하지 않습니다.
- 공통 규칙과 팀 합의 문서는 Pull Request 승인 후 변경합니다.
- 다른 팀원의 문서를 임의로 삭제하거나 덮어쓰지 않습니다.
- 중요한 결정은 관련 Issue, PR 또는 회의록 링크를 남깁니다.
- 파일을 교체하기보다 Git 변경 이력이 유지되는 방식으로 수정합니다.
- 기업 민감정보, 개인정보, 계정정보와 비밀번호는 저장하지 않습니다.

### 문서 상태

중요 문서의 상단에는 다음 정보를 작성합니다.

```text
작성자: GitHub ID 또는 이름
최종 수정일: YYYY-MM-DD
상태: 초안 | 검토중 | 확정
```

| 상태 | 의미 |
|---|---|
| `초안` | 작성자의 아이디어이며 팀 합의 전 상태 |
| `검토중` | 팀 또는 기업 피드백을 받고 있는 상태 |
| `확정` | 팀이 합의했거나 기업 확인을 마친 기준 문서 |

`확정` 상태의 문서를 변경할 때는 변경 이유를 Issue 또는 PR에 기록합니다.

## 2. 문서 폴더 구조

각 팀원은 `docs` 아래에 자신의 이름 또는 팀에서 합의한 식별자로 폴더를 하나 만들고, 모든 개인 문서를 해당 폴더 안에서 관리합니다.

```text
docs/
  JinsuBae2/
    proposal.md
    questionnaire.md
    schedule.md
  Rinhaze/
    proposal.md
  teammate-name/
    proposal.md
```

문서 작성 방법은 [docs/README.md](docs/README.md)를 확인하세요.

## 3. 현재 프로젝트 주제

- 협력업체 정보 통합관리
- 계약 및 인증 자료 관리
- 계약 및 인증 만료 알림
- 발주 및 납기자료 관리 방안 검토

## 4. 기본 브랜치 규칙

### main 브랜치

- `main`은 항상 팀원이 읽고 검토할 수 있는 상태로 유지합니다.
- `main`에 직접 커밋하거나 강제 푸시하지 않습니다.
- 모든 변경은 작업 브랜치에서 작성하고 Pull Request로 병합합니다.
- 작성자를 제외한 팀원 1명 이상의 승인을 받은 뒤 병합합니다.
- 모든 리뷰 대화를 해결한 뒤 병합합니다.
- `Squash and merge`를 기본 병합 방식으로 사용합니다.
- 작업이 끝난 브랜치는 병합 후 삭제합니다.

### 권장 GitHub 보호 설정

- Require a pull request before merging
- Required approvals: 1
- Dismiss stale pull request approvals when new commits are pushed
- Require conversation resolution before merging
- Block force pushes
- Block deletions

## 5. 작업 브랜치 규칙

브랜치에는 `:`와 공백을 사용할 수 없으므로 다음 형식을 사용합니다.

```text
<type>/<기능>-<한글-내용>
```

작성자 ID는 브랜치 이름에 넣지 않습니다. 설명에 띄어쓰기가 필요하면 하이픈으로 구분합니다.

| 유형 | 용도 | 예시 |
|---|---|---|
| `feat` | 새로운 기능 개발 | `feat/만료알림-계약-만료-조회` |
| `fix` | 기능 또는 문서 오류 수정 | `fix/만료알림-날짜-계산-오류` |
| `docs` | 기획서와 문서 작성·수정 | `docs/기획서-미팅-질문지-추가` |
| `refactor` | 동작 변경 없는 구조 개선 | `refactor/알림-서비스-구조-분리` |
| `test` | 테스트 추가·수정 | `test/만료알림-경계값-검증` |
| `chore` | 저장소 설정과 템플릿 변경 | `chore/저장소-PR-템플릿-추가` |

한 브랜치에서는 하나의 목적만 다룹니다.

## 6. 커밋 규칙

커밋 메시지는 다음 형식을 사용합니다.

```text
<type>(<기능>): <한글 내용>
```

예시:

```text
fix(만료알림): 계약 만료일 계산 오류 수정
feat(협력업체): 협력업체 상세 조회 기능 추가
docs(기획서): 기업 미팅 질문지 추가
chore(저장소): PR 템플릿 추가
```

작성자 ID는 커밋 메시지에 넣지 않습니다.

| 유형 | 용도 |
|---|---|
| `feat` | 새로운 기능 추가 |
| `fix` | 기능·문서 오류 수정 |
| `docs` | 문서 추가·수정 |
| `refactor` | 동작 변경 없는 코드 구조 개선 |
| `test` | 테스트 추가·수정 |
| `chore` | 설정, 템플릿, 도구 변경 |

커밋 작성 시 다음 기준을 따릅니다.

- 기능은 변경 범위를 알아볼 수 있는 짧은 명사로 작성합니다.
- 한글 내용은 무엇을 변경했는지 구체적으로 작성합니다.
- 제목 끝에 마침표를 붙이지 않습니다.
- 한 커밋에는 하나의 논리적인 변경만 포함합니다.
- `수정`, `업데이트`, `작업`처럼 내용을 알 수 없는 표현만 단독으로 사용하지 않습니다.

## 7. Pull Request 규칙

### 제목

PR 제목도 커밋과 동일한 형식을 사용합니다.

```text
docs(기획서): 기업 미팅 질문지 추가
```

### 본문

저장소의 PR 템플릿에 따라 다음 내용을 작성합니다.

- 변경 목적과 배경
- 주요 변경사항
- 확인 방법
- 관련 Issue
- 리뷰어가 확인해야 할 부분

### 변경 범위

- 개인 문서는 원칙적으로 자신의 `docs/<이름>/` 폴더만 수정합니다.
- README, 템플릿 또는 협업 규칙 변경은 별도의 PR로 분리합니다.
- 관련 없는 문서 정리나 표현 변경을 함께 포함하지 않습니다.
- 기업 민감정보와 실제 개인정보가 포함되지 않았는지 확인합니다.

### 리뷰와 병합

- 작성자는 PR을 먼저 자체 검토한 뒤 리뷰를 요청합니다.
- 리뷰어는 내용, 파일 위치, 링크와 민감정보 포함 여부를 확인합니다.
- 수정 요청을 반영하거나 반영하지 않는 이유를 댓글로 남깁니다.
- 승인 1개와 모든 리뷰 대화 해결 후 `Squash and merge`로 병합합니다.

## 8. Issue 규칙

### Issue를 만드는 경우

- 새로운 기획 또는 조사 작업
- 미팅 전 확인해야 할 질문
- 문서 오류 또는 누락
- 팀의 결정이 필요한 논점
- 추후 서비스 기능과 기술 작업

단순 오탈자를 즉시 수정하는 경우에는 Issue를 생략할 수 있습니다.

### 제목

```text
[유형] 구체적인 작업 또는 문제
```

예시:

- `[기획] 계약 만료 알림 기준 조사`
- `[문서] 미팅 질문지 보완`
- `[결정] 팀원 폴더명 표기 방식 확정`
- `[버그] README 링크 오류 수정`

### 본문

- 배경 또는 문제
- 수행할 작업
- 완료 조건
- 필요한 자료 또는 선행 작업
- 담당자와 목표일
- 관련 문서 또는 PR 링크

### 라벨 권장안

| 라벨 | 의미 |
|---|---|
| `planning` | 기획과 요구사항 |
| `documentation` | 문서 작성·수정 |
| `meeting` | 기업 또는 팀 미팅 |
| `decision` | 팀 합의가 필요한 항목 |
| `bug` | 오류와 잘못된 정보 |
| `security` | 개인정보와 보안 |
| `blocked` | 외부 확인 또는 선행 작업 필요 |

## 9. 기본 작업 흐름

```bash
git switch main
git pull origin main
git switch -c docs/기획서-미팅-질문지-추가

# 문서 작성 후
git add docs/<이름>/
git commit -m "docs(기획서): 기업 미팅 질문지 추가"
git push -u origin docs/기획서-미팅-질문지-추가
```

푸시 후 GitHub에서 Pull Request를 만들고 팀원에게 리뷰를 요청합니다.
