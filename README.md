# 한국농산 캡스톤 디자인 기획 자료

한국농산 캡스톤 디자인 프로젝트의 팀원별 초기 기획 자료를 모으는 저장소입니다.

이 저장소는 팀 기획안을 통합하기 전에 세 명의 팀원이 각자 조사한 내용, 아이디어, 미팅 질문과 개발 계획을 공유하는 공간입니다. 개인 문서는 원본 그대로 관리하고, 통합 기획서는 팀 논의 후 별도로 작성합니다.

## 1. 저장소 운영 원칙

이 저장소는 프로젝트의 공식 문서 기준점으로 사용합니다. 기획, 일정, 회의 결과, 협업 규칙과 주요 결정은 구두로만 남기지 않고 이 저장소에 기록합니다.

- README는 저장소 구조와 협업 규칙의 기준 문서입니다.
- 개인 기획은 `docs/<이름>/`에서 작성자별로 관리합니다.
- 팀 합의 전에는 개인 의견을 확정된 요구사항처럼 표현하지 않습니다.
- 공통 규칙과 팀 합의 문서는 팀원에게 변경 내용을 공유한 뒤 수정합니다.
- 다른 팀원의 문서를 임의로 삭제하거나 덮어쓰지 않습니다.
- 중요한 결정은 관련 Issue, 커밋 또는 회의록 링크를 남깁니다.
- 파일을 교체하기보다 Git 변경 이력이 유지되는 방식으로 수정합니다.
- 기업 민감정보, 개인정보, 계정정보와 비밀번호는 저장하지 않습니다.

### 문서 상태

중요 문서의 상단에는 다음 정보를 작성합니다.

```text
작성자: GitHub ID 또는 이름
최종 수정일: YYYY-MM-DD
상태: 초안 | 검토중 | 확정
```

| 상태 | 의미 |
|---|---|
| `초안` | 작성자의 아이디어이며 팀 합의 전 상태 |
| `검토중` | 팀 또는 기업 피드백을 받고 있는 상태 |
| `확정` | 팀이 합의했거나 기업 확인을 마친 기준 문서 |

`확정` 상태의 문서를 변경할 때는 변경 이유를 Issue 또는 커밋에 기록합니다.

## 2. 문서 폴더 구조

각 팀원은 `docs` 아래에 자신의 이름 또는 팀에서 합의한 식별자로 폴더를 하나 만들고, 모든 개인 문서를 해당 폴더 안에서 관리합니다.

```text
docs/
  JinsuBae2/
    proposal.md
    questionnaire.md
    schedule.md
  Rinhaze/
    proposal.md
  teammate-name/
    proposal.md
```

문서 작성 방법은 [docs/README.md](docs/README.md)를 확인하세요.

## 3. 현재 프로젝트 주제

- 협력업체 정보 통합관리
- 계약 및 인증 자료 관리
- 계약 및 인증 만료 알림
- 발주 및 납기자료 관리 방안 검토

## 4. 현재 문서 저장소 운영 규칙

### main 브랜치

- `main`은 항상 팀원이 읽고 검토할 수 있는 상태로 유지합니다.
- 현재 저장소는 기획 자료 공유용이므로 Pull Request를 필수로 사용하지 않습니다.
- 자신의 문서 폴더 작업은 최신 `main`을 받은 뒤 직접 커밋하고 푸시할 수 있습니다.
- 다른 팀원이 같은 파일을 수정 중이면 작업 전에 먼저 공유합니다.
- 공통 README와 규칙을 크게 변경할 때는 팀원에게 내용을 공유합니다.
- 강제 푸시는 사용하지 않습니다.
- 규모가 크거나 리뷰가 필요한 변경은 선택적으로 작업 브랜치와 PR을 사용합니다.

## 5. 작업 브랜치 규칙

작업 브랜치가 필요한 경우 영문 소문자와 하이픈으로 작성합니다.

```text
<type>/<scope>-<short-description>
```

작성자 ID는 브랜치 이름에 넣지 않습니다.

| 유형 | 용도 | 예시 |
|---|---|---|
| `feat` | 새로운 기능 개발 | `feat/expiry-alert-list` |
| `fix` | 기능 또는 문서 오류 수정 | `fix/expiry-date-calculation` |
| `docs` | 기획서와 문서 작성·수정 | `docs/meeting-questionnaire` |
| `refactor` | 동작 변경 없는 구조 개선 | `refactor/notification-service` |
| `test` | 테스트 추가·수정 | `test/expiry-boundary-cases` |
| `chore` | 저장소 설정과 템플릿 변경 | `chore/pr-template` |

한 브랜치에서는 하나의 목적만 다룹니다.

## 6. 커밋 규칙

커밋 메시지는 다음 형식을 사용합니다.

```text
<type>(<기능>): <한글 내용>
```

예시:

```text
fix(만료알림): 계약 만료일 계산 오류 수정
feat(협력업체): 협력업체 상세 조회 기능 추가
docs(기획서): 기업 미팅 질문지 추가
chore(저장소): PR 템플릿 추가
```

작성자 ID는 커밋 메시지에 넣지 않습니다.

| 유형 | 용도 |
|---|---|
| `feat` | 새로운 기능 추가 |
| `fix` | 기능·문서 오류 수정 |
| `docs` | 문서 추가·수정 |
| `refactor` | 동작 변경 없는 코드 구조 개선 |
| `test` | 테스트 추가·수정 |
| `chore` | 설정, 템플릿, 도구 변경 |

커밋 작성 시 다음 기준을 따릅니다.

- 기능은 변경 범위를 알아볼 수 있는 짧은 명사로 작성합니다.
- 한글 내용은 무엇을 변경했는지 구체적으로 작성합니다.
- 제목 끝에 마침표를 붙이지 않습니다.
- 한 커밋에는 하나의 논리적인 변경만 포함합니다.
- `수정`, `업데이트`, `작업`처럼 내용을 알 수 없는 표현만 단독으로 사용하지 않습니다.

## 7. 개발 저장소 Pull Request 규칙

이 규칙은 추후 실제 서비스를 개발할 별도 저장소에 적용합니다. 현재 문서 저장소에서는 PR이 필수가 아닙니다.

### 제목

PR 제목도 커밋과 동일한 형식을 사용합니다.

```text
feat(만료알림): 계약 만료 목록 조회 기능 추가
```

### 본문

저장소의 PR 템플릿에 따라 다음 내용을 작성합니다.

- 변경 목적과 배경
- 주요 변경사항
- 확인 방법
- 관련 Issue
- 리뷰어가 확인해야 할 부분

### 변경 범위

- 하나의 PR에서는 하나의 Issue 또는 하나의 목적만 다룹니다.
- 관련 없는 리팩터링과 문서 정리를 함께 포함하지 않습니다.
- 기능 변경에 필요한 테스트와 문서를 함께 수정합니다.
- 기업 민감정보와 실제 개인정보가 포함되지 않았는지 확인합니다.

### 리뷰와 병합

- 작성자는 PR을 먼저 자체 검토한 뒤 리뷰를 요청합니다.
- 리뷰어는 내용, 파일 위치, 링크와 민감정보 포함 여부를 확인합니다.
- 수정 요청을 반영하거나 반영하지 않는 이유를 댓글로 남깁니다.
- 승인 1개와 모든 리뷰 대화 해결 후 `Squash and merge`로 병합합니다.

## 8. Issue 규칙

현재 문서 저장소에서는 필요할 때만 Issue를 사용합니다. 추후 개발 저장소에서는 모든 기능, 수정과 기술 작업을 Issue로 먼저 등록합니다.

### Issue를 만드는 경우

- 새로운 기획 또는 조사 작업
- 미팅 전 확인해야 할 질문
- 문서 오류 또는 누락
- 팀의 결정이 필요한 논점
- 추후 서비스 기능과 기술 작업

단순 오탈자를 즉시 수정하는 경우에는 Issue를 생략할 수 있습니다.

### 제목

```text
[유형] 구체적인 작업 또는 문제
```

예시:

- `[기획] 계약 만료 알림 기준 조사`
- `[문서] 미팅 질문지 보완`
- `[결정] 팀원 폴더명 표기 방식 확정`
- `[버그] README 링크 오류 수정`

### 본문

- 배경 또는 문제
- 수행할 작업
- 완료 조건
- 필요한 자료 또는 선행 작업
- 담당자와 목표일
- 관련 문서 또는 PR 링크

### 라벨 권장안

| 라벨 | 의미 |
|---|---|
| `planning` | 기획과 요구사항 |
| `documentation` | 문서 작성·수정 |
| `meeting` | 기업 또는 팀 미팅 |
| `decision` | 팀 합의가 필요한 항목 |
| `bug` | 오류와 잘못된 정보 |
| `security` | 개인정보와 보안 |
| `blocked` | 외부 확인 또는 선행 작업 필요 |

## 9. 현재 문서 저장소 작업 흐름

```bash
git switch main
git pull origin main

# 문서 작성 후
git add docs/<이름>/
git commit -m "docs(기획서): 기업 미팅 질문지 추가"
git push origin main
```

변경 규모가 크거나 팀원 검토가 필요하면 `docs/meeting-questionnaire`와 같은 영문 브랜치를 만들어 선택적으로 PR을 사용합니다.

## 10. 향후 개발 저장소 기본 작업 흐름

실제 서비스 개발은 별도 저장소에서 진행하며 다음 순서를 기본으로 사용합니다.

1. **Issue 생성**: 작업 배경, 요구사항, 완료 조건과 담당자를 작성합니다.
2. **작업 준비**: 최신 `main`을 받고 Issue에 대응하는 영문 브랜치를 생성합니다.
3. **작업 수행**: 기능 구현, 테스트와 필요한 문서 수정을 함께 진행합니다.
4. **커밋 및 푸시**: 커밋 컨벤션에 맞춰 논리적인 단위로 커밋하고 원격 브랜치에 푸시합니다.
5. **Pull Request 생성**: 관련 Issue를 연결하고 변경사항과 검증 결과를 작성합니다.
6. **리뷰 및 승인**: 작성자를 제외한 팀원 1명 이상이 리뷰하고 승인합니다.
7. **병합**: 모든 리뷰 대화를 해결한 뒤 `Squash and merge`로 `main`에 병합합니다.
8. **정리**: 병합된 작업 브랜치를 삭제하고 Issue가 종료됐는지 확인합니다.

```bash
# 1. Issue 생성 후 작업 시작
git switch main
git pull origin main
git switch -c feat/expiry-alert-list

# 2. 구현과 검증 후 커밋·푸시
git add .
git commit -m "feat(만료알림): 계약 만료 목록 조회 기능 추가"
git push -u origin feat/expiry-alert-list

# 3. GitHub에서 PR 생성 → 리뷰 승인 → Squash and merge
```

개발 저장소의 `main`에는 PR 없이 직접 푸시하지 않습니다.
