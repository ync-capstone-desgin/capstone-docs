- 작성자: JinsuBae2
- 최종 수정일: 2026-09-22
- 상태: 초안

## 1. 설계 목적과 원칙

협력업체, 계약, 인증과 만료 알림의 핵심 흐름을 검증할 최소 구조를 정의한다. 기술 스택과 기업 시스템 연동은 확정하지 않고 미팅 후 변경하기 쉬운 논리적 경계를 우선한다.

- 1차 PoC는 협력업체·계약·인증·만료 알림에 집중한다.
- 발주·납기는 조회 중심의 확장 영역으로 분리한다.
- 업무 규칙과 알림 기준은 설정 가능한 값으로 관리한다.
- 실제 개인정보 대신 비식별 샘플 데이터를 사용한다.
- 외부 시스템과 알림 채널은 인터페이스만 고려하고 구현 여부는 추후 결정한다.

## 2. 논리 구조

```text
[사용자]
   |
   v
[웹 화면]
   |-- 대시보드
   |-- 협력업체 관리
   |-- 계약·인증 관리
   |-- 만료 예정 조회
   `-- 발주·납기 조회 선택
   |
   v
[애플리케이션 API]
   |-- 협력업체 서비스
   |-- 계약 서비스
   |-- 인증 서비스
   |-- 만료 판정 서비스
   |-- 알림 서비스
   `-- 파일 메타데이터 서비스
   |                   |
   v                   v
[관계형 DB]       [파일 저장소 선택]
   |
   v
[정기 실행 작업: 만료 계산 → 알림 대상 생성 → 이력 기록]
```

## 3. 구성요소 책임

| 구성요소 | 책임 | 확인사항 |
|---|---|---|
| 웹 화면 | 입력, 검색, 현황 시각화 | 사용자별 메뉴 차이 |
| 협력업체 서비스 | 업체 기본정보와 상태 관리 | 필수 항목과 상태 종류 |
| 계약 서비스 | 계약기간, 상태, 담당자, 파일 참조 | 자동연장·무기한 계약 |
| 인증 서비스 | 인증 종류, 유효기간, 갱신이력 | 인증 종류와 규칙 |
| 만료 판정 서비스 | 정상·예정·만료 상태 계산 | 경계일과 휴일 처리 |
| 알림 서비스 | 대상 생성, 발송 요청, 처리이력 | 채널·수신자·반복 규칙 |
| 발주·납기 서비스 | 업체별 현황 조회 | PoC 포함 수준 |
| 파일 저장소 | 계약서·인증서 파일 보관 | 보안·보관정책 |

## 4. 핵심 데이터 흐름

### 계약·인증 등록

1. 사용자가 협력업체를 선택한다.
2. 기본정보와 유효기간을 입력한다.
3. 시스템이 필수값과 날짜 순서를 검증한다.
4. 데이터와 선택적인 파일 참조를 저장한다.
5. 현재 날짜를 기준으로 만료 상태를 표시한다.

### 만료 대상 생성

1. 정기 작업이 활성 계약과 인증을 조회한다.
2. 만료일과 알림 기준일을 비교한다.
3. 동일 대상·기준의 기존 알림을 확인한다.
4. 새 알림 대상을 생성하고 이력을 기록한다.
5. 대시보드에 표시하고 확정된 채널이 있으면 발송한다.

## 7. 상태 계산 초안

```text
expiry_date 없음             -> 확인 필요
expiry_date < 오늘           -> 만료
오늘 <= expiry_date <= 기준일 -> 만료 예정
expiry_date > 기준일         -> 정상
```

날짜에 따른 만료상태와 담당자의 갱신 처리상태는 분리한다.

## 8. 오류와 보안

- 종료일이 시작일보다 빠르면 저장하지 않는다.
- 필수 날짜가 없으면 확인 필요 상태로 표시한다.
- 동일 업체와 문서번호의 중복 등록을 경고한다.
- 알림 발송 실패와 업무 데이터 저장 실패를 분리해 기록한다.
- 계정, 토큰과 실제 문서를 Git에 저장하지 않는다.
- 파일 접근은 업무 데이터와 같은 권한 기준을 적용한다.
- 실제 서비스 전환 전 접근 로그, 백업, 암호화와 보관기간을 확정한다.
